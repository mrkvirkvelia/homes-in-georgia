# Сценарии старой CRM vs новая CRM

Источник: репозиторий `PlatformDGE/-rentintbilisi-crm` (публичный, прочитан через `gh api`; основной файл `index.html` ≈ 6100 строк, мини-приложение «Homes in Georgia · CRM») + `apps-script/crm-auth.gs`.
Сверка: код `homes-in-georgia` (прочитан, не угадан). Дата: 2026-11-11. Ничего не менялось и не коммитилось.

> **Важное ограничение.** В репозитории лежит только **клиент** (HTML/JS в Telegram Mini App и на GitHub Pages). Серверная часть, которая принимает `?action=submit`, шлёт посты в топики, сохраняет в таблицы и по триггерам напоминает — это отдельный Apps Script (`API_URL`, `GAS_URL`), которого в репо нет. Его логику (saveRentalWithT0, saveRerented, saveT14/checkT14Reminders, saveCalc, checkExpiringContracts, parseDealMessage, findContractByKadastr) покрывает локальный `old/script_from_apps_scripts.js`; здесь я описываю то, что видно из клиента. Что именно приходит из сервера (например, поля `contracts` кабинета) помечено «не проверено».
> Также в репо нет парсера `#Rented`-постов (parseDealMessage) — он только на сервере.

## 1. Сценарии старой CRM

### 1.1 Сделки (главное)

**Экран «Калькулятор» (`tab-calc`, «Calculator + Report + T0», кнопка «🚀 Зафиксировать сделку»).** Единая форма: расчёт + отчёт `#Rented` + оценка T0. Отправляет `send('rental', …)` → сервер.

Поля формы:
1. **База расчёта:** сумма сделки $, тип (аренда 50% / продажа 3%), комиссия агентства $ (авто = цена × %), число сделок в потоке.
2. **Объект:** ссылка на объявление* и кадастровый номер* (обязательны); эксклюзив / неэксклюзив; тип (аренда/продажа); подтип аренды (долгосрок 50% / коммерция 100%).
3. **Участники:** агент* (список агентов + рекрутов, уровень 50/70/90 подтягивается), рекрут/агент (показ), «кто передал клиента», наставник.
4. **Клиент и собственник:** имя, Telegram/телефон; даты аренды «От*/До*».
5. **Подтверждение эксклюзива** (если эксклюзив): устная договорённость или письменная + **скриншот** (до 8 МБ, сжимается до 1400 px, уходит base64 в запросе). Без подтверждения отправить нельзя.
6. **T0 H2O:** три оценки 1–3 (Client Delivery / Owner Result / Process Integrity), сумма ≥7/9 = «чистая», иначе «грязная»; комментарий агента.
7. Предпросмотр текста поста; черновик автосохраняется в localStorage (`draftSave('calc')`).

**Расчёт комиссии.** Две версии в одном файле, последняя перекрывает первую:
- *Старые сценарии 0–7* (`COMMISSION_RULES`, всё в % от комиссии агентства): 0 агент сам (эксклюзив = уровень, иначе 50); 1 агент + показ рекрута (агент 30/50/70, показ 20); 2 агент передал (10/30/50 + рекрут 40); 3 рекрут 5 сделок (70/30 + 20); 4 рекрут 10 сделок (наставник 25, рекрут 50, платформа 25); 5 объект рекрута (<10 сд.: 25/50/25; ≥10: 15/70/15); 6 передача клиента (источник 10%, агент уровень−10, платформа 100−уровень); 7 ручное (свои %, + «внешний агент»); **Rerented** — комиссия 0, строка «🔄 RERENTED», в счётчик/аналитику не идёт.
- *Molecula 90/10* (активная, `moleculeRows`, пять осей): «делаю сам» (лестница 50/70/90 по числу эксклюзивов: 1–10 / 11–100 / >100), «участвую» (показ+договор 20%, только подписание 10%, клиент: совместный показ 20 / передача 10 / внешний 30; чужой эксклюзив полный цикл 40), «передаю» (наставник 50; поток 15/25 + агент; хранитель потока 1–5%), «создаю направление» (тест 50 или 15/25), «внешний контур» (внешний 50, куратор 25, платформа 25). Платформа = остаток. Строки распределения уходят на сервер (`dist_rows`, `molecule_distribution`, `molecule_axis`).
- Размер платформы, агента, рекрута, источника клиента (`recruit_commission`, `platform_commission`, `agent_commission_final`, `client_src`) считается в клиенте и отправляется готовыми цифрами.

**Что куда уходит (из клиента + локального GAS).** `#Rented | Deal #N | #Exclusive/#NonExclusive | уровень%` с блоками Link / Price / Commission / Platforms Commission / `#Agent Commission` / рекрут / «Передал клиента: …» / подтверждение эксклюзива / Cadastral / Client / Owner / Date of Rent / H2O T0 (X/Y/Z → чистая/грязная) / комментарий → топики рабочей группы (`DEAL_TOPICS`, дубли в Rerented); запись в листы (Reports_Deals, счётчики агента, «Rent_out_Apartment»). Номер сделки `Deal #N` — по счётчику эксклюзивов агента.

**Отдельный режим «Калькулятор» (`tab-deals`/`d-*`):** простой расчёт цена × % → агент/платформа по уровню 50/70/90, «зафиксировать расчёт» (`send('calc')`, лист/топик расчётов); неэксклюзив «не идёт в зачёт 90/10».

**Поиск договора по кадастру:** при вводе ≥5 символов кадастра (debounce 0,8 с) `findContract` в Google Drive → «✓ Договор найден: …» + встроенный PDF-просмотр, иначе «✗ не найден в папке».

**T14 (`form-t14`).** Форма «Через 14 дней после сдачи»: объект/адрес, агент, дата сделки, H2O 1–3 ×3, «изменения», жалобы да/нет + текст, итог чистая/грязная, комментарий. Напоминания за T14 — серверный триггер (в репо нет; по локальному GAS: `checkT14Reminders`).

**Напоминания по договорам.** Клиентская часть — кабинет агента: баннер «⚠️ Заканчивается через N дн.» для договоров с `daysLeft` 0–30 (красный ≤7, оранжевый ≤30), список договоров (адрес, цена/мес, клиент, собственник с кнопками позвонить/копировать, период, «🔄 Rerented / 📄 Новый договор» — `renewType`), «Истёк N дн. назад». Рассылка в Telegram — на сервере (`checkExpiringContracts`).

### 1.2 Договоры (`tab-contract`)
Мастер из 4 шагов (Type → Lang → Details → Review): тип (квартира / коммерция / продажа), язык (GEO/RU/EN), поля: дата договора, собственник (ФИО, ID, дата рождения), арендатор/покупатель (ФИО, ID, ДР), кадастр, адрес, этаж, квартира, площадь, даты аренды, срок (мес.), цена/мес, залог, **«с питомцами» (залог за питомца = 50% основного)**, день оплаты 1–31; для продажи — цена и дата передачи. Отправка JSONP на отдельный GAS → создаёт DOC в Drive и PDF; результат: «Редактировать DOC», «Скачать PDF», предпросмотр PDF. Автоподсчёт `one_month` (договор на один месяц).

### 1.3 Объекты
- **«Объекты» (`tab-objects`)**: лента актуальных публикаций из двух Telegram-каналов + фильтр по агенту; «+ Объект» → Post Generator (`post-generator-modern.html`, отдельная страница).
- **Make Foto From Platform (`form-makefoto`)**: адрес*, дата/время*, агент*, собственник, телефон, ссылка → пост в топик. Предпросмотр текста.
- **Property Check (`form-check`)**: поиск по телефону и/или адресу в базе собственников (`checkProperty`): 🟢 не найдено / 🟡 возможное совпадение (1 поле) / 🔴 уже в базе (телефон+адрес). Показывает источник, собственника, телефон, адрес, ссылку, агента, дату фото, статус (Published…).
- **Object Registry MVP (демо, localStorage, `app.js` + `lib-repository.js`)**: форма объекта (source_type, URL, owner, phone, address, district, cadastral, price, rooms, area, агент), проверка точных дублей (нормализованный URL, external ID MyHome/SS, кадастр, телефон+адрес; архив тоже), статус ASSIGNED, задача MAKE_PHOTO, журнал действий, Telegram-уведомление (mock). Тесты на нормализацию. Это прототип, не боевая система.
- Blueprint (`RENT_IN_TBILISI_PLATFORM_BLUEPRINT.md`) — план: жизненный цикл объекта, Owners/Clients, Publishing Engine, duplicate_score, Contracts, Agents; в основном **не реализован** в этом репо.

### 1.4 Заявки / клиенты / показы
В старой CRM **нет** воронки заявок и клиентов. Есть только:
- **Показ** (`form-showing`, рекрут): рекрут, наставник, адрес, ссылка, Telegram клиента, дата, результат (отказ/думает), прогресс 0/15.
- **Календарь в кабинете**: неделя со свайпом, события = показы + «Конец договора»; форма «+ Показ» (дата, время, ссылка, адрес с автоподстановкой собственника из базы по адресу, собственник/телефон, клиент/телефон, рекрут/второй агент, комментарий). Блок «Календарь» в нижнем меню.

### 1.5 Отчёты агентов/рекрутов
- **Фото / Показ / Расклейка** (`form-photo/showing/stickers`): рекрут + наставник, район/адрес, ссылка из Advertising, дата; расклейка — район, число стикеров, скрин карты. Счётчик 0/15 на каждый вид (план «15 раз» с наставником).
- **Daily Report**: автор, дата, звонки (всего / not agreed / agreed), стикеры + район, фото + адрес + Photo Master, показы + адрес + Showing Master, предпросмотр.
- **General Report**: автор, секции фото/показы/расклейка/calling/сделки (ссылки, участник, адрес/район), в топики.
- Всё уходит в рабочую группу (топики Фото/Показы/Расклейка/Daily/General) и листы.

### 1.6 Админка и команда
- Вход: Telegram Mini App (`initData`) либо веб — **Telegram Login Widget** (`crm-auth.gs`, сессия 30 дней), **самрегистрация** (телефон + дата рождения → лист `Agent_Accounts`), доступ только если Telegram есть в листах «Агенты»/«Рекруты», выключили — выкинет.
- Админ (по SUPER_IDS/ролям): список агентов/рекрутов (вкл/выкл, уровень 50/70/90), добавить агента/рекрута, **повысить рекрута до агента**, бегущая строка (срочные сообщения над дашбордом), настройки метрик и секций дашборда.
- Профиль агента: счётчики сделок, прогресс уровня, контакты, список договоров и сделок (последние 10, с типом подтверждения эксклюзива), список других агентов (для админа).
- Знания: «Стандарты 90/10», викторина (20 вопросов), лестница роста, база знаний, новости (топик канала), правила наставника (25% первые 10 сделок, 15% следующие 90).

### 1.7 Дашборд и аналитика
Дашборд: сделки периода (месяц/квартал/всё), комиссия платформы, активные объекты, график комиссии по месяцам, районы, комнатность, последние сделки, топ-5 агентов по сдачам, объекты за неделю; Telegram-аналитика (топ-10 по репостам 10:00–22:00 по Тбилиси, GitHub Action `update-telegram-top10.yml`).

### 1.8 Публичный сайт и автоматизации GitHub (не CRM, но в репо)
`site/` — публичный каталог (rent/sale/commercial/homes/daily/car), карта, share-страницы, i18n; Actions: `update-public-catalog`, `geocode-public-catalog`, `deploy-pages`, `update-telegram-top10`; `site-analytics.gs` (аналитика сайта). Это маркетинговый сайт, а не сценарий сделки.

### 1.9 Напоминания и триггеры
- T14: напоминание агенту/в топик через 14 дней (сервер, не проверено по этому репо).
- Конец договора: кабинет показывает ≤30 дней; рассылка — сервер (в локальном GAS `checkExpiringContracts`).
- Telegram top-10: Action по расписанию. Обновление каталога сайта: Actions.

## 2. Сравнение с новой CRM

Легенда: **есть / частично / нет**. Файлы относительно `homes-in-georgia/`.

### Сделки

| Сценарий старой CRM | Статус | Где в новой / комментарий |
|---|---|---|

| Подтверждение сделки оператором, `pending → confirmed`, отмена | **есть, нового** | `deals.confirm/cancel`; в старой подтверждения не было |
| Агентский уровень 50/70/90, авто-повышение по эксклюзивам, номер сделки `Deal #N` | **есть** | `users.level_for/effective_level`, `deals.confirm` (agent_deal_num, level_up) |
| Комиссия: цена×% (аренда 50 / коммерция 100 / продажа 3), ручная сумма | **есть** | `deals.default_commission_pct`; агенту % фиксирован, вручную может только staff |

| Сценарии 0–7 (агент+показ, передал, рекрут 5/10 сд., объект рекрута, ручное) в самой сделке | **частично** | Есть в отдельном `frontend/src/pages/Calc.tsx` (порт `COMMISSION_RULES` и Molecula), но **не связаны с формой сделки и не сохраняются**; в DealForm их нет |

| Наставник (25% первые 10 / 15% следующие 90 с эксклюзивов рекрута) | **нет** | `mentor_id` у пользователя есть (`analytics.py`, Admin), но в `deals.calc` доли наставника нет; нет поля/строки в сделке |
| **Rerented** (комиссия 0, без счётчика) | **есть** | `is_rerented` → `comm=0` (`deals.calc`), отдельный текст `rented_text`; счётчик эксклюзивов инкрементится только при `is_exclusive` (проверить, что rerented не эксклюзив — не проверено) |
| Подтверждение эксклюзива (устно / письменно + скриншот) | **нет** | В `DealForm`/`models` нет поля `exclusive_proof*` (grep пусто). Эксклюзив — просто switch |
| Данные клиента/собственника, даты аренды | **есть** | `DealForm` (+ ДР в модели, в форме нет — `client_birth/owner_birth` только в `FIELDS`) |
| Автозаполнение из лида/объекта | **есть, нового** | `lead_id`, `properties.deal_fields` |
| T0 H2O (3 оценки + чистая/грязная + комментарий) | **частично** | `DealForm` блок «День 0»: 0–3 (в старой 1–3), оценки + комментарий есть; **«чистая/грязная» нет в форме** (в старой ≥7/9 → авто; `rented_text` умеет, `evaluations` — не проверено); алерт при ≤1 → `notify.evaluation_alert` |
| Текст `#Rented` в топик рабочей группы | **осознанно нет** | `rented_text()` есть (отдаётся в `GET /deals/{id}`), но `notify.deal_confirmed` шлёт **только агенту** (решение Станислава 2026-11-08, строка docstring). Для истории/чтения в CRM — ок |
| Расчёт-отчёт без сделки (`send('calc')`) в топик | **частично** | `reports.build_posts("calc")` есть, формы «зафиксировать расчёт» в `Calc.tsx` не проверено |
| Парсинг сделок из `#Rented`-постов (parseDealMessage) | **частично** | Не как рантайм-парсер; история заведена одноразовым импортёром `importers/legacy_objects.py` («Rented/Sold By Agent» → deals) и `sheets_csv.py`. Новые «ручные» посты в Telegram-группе больше не разбираются — не проверено |
| Поиск договора по кадастру (Drive) | **частично** | `GET /deals/find?cadastral=` ([business.py:96](backend/app/api/business.py), `deals.find`, ilike) и `api.deals.find` в `api/index.ts`, **но фронт его не вызывает** (grep: только mock). Drive/PDF-предпросмотра нет |

## 3. Что стоит доделать (по важности)

1. **Неэксклюзив = 50% (а не уровень).** `deals.calc` игнорирует `is_exclusive`; агент 90% при неэксклюзиве получает 90%, а раньше 50%. Прямые деньги. Править в `calc()` + тест; обновить подпись «Платформа (X%)» в `DealForm`.
2. **Сценарии распределения в самой сделке.** Сейчас в сделке только «уровень + ручной % рекрута + 10% источнику». Нужно либо подключить сценарии/Molecula из `Calc.tsx` (бэкенд тоже должен хранить распределение: агент / рекрут / наставник / источник / платформа, `molecule_axis`), либо явно решить, что деньги по ним считает оператор вручную (`commission_total`/`platform_amount`).
3. **Наставник и источник клиента как люди.** Поле «наставник» с долей (25/15%) и выбор **конкретного агента/рекрута** в `client_src` (сейчас список соцсетей) — иначе отчёт по выплатам неполный.
4. **Подтверждение эксклюзива** (устно/письменно + скриншот) — правило «нельзя выдавать неэксклюзив за эксклюзив» теперь нигде не проверяется. Хотя бы поле + файл + обязательность при `is_exclusive`, видно оператору при подтверждении.
5. **Поиск договора по кадастру в UI.** Бэкенд (`/deals/find`) готов, фронт не вызывает. Подключить в `Contracts.tsx`/`DealForm` (поле кадастра) и решить про хранение готового договора (сейчас договор нигде не сохраняется, без Drive).
6. **T0: итог «чистая/грязная» по сумме** (≥7/9 в старой шкале 1–3; в новой шкала 0–3, порог надо пересчитать) + показывать в `rented_text`/карточке сделки. Проверить, что `evaluations.create` заполняет `result`.
7. **Признак продления у конца договора** (`renewType`: Rerented / новый договор) и отметка в `Expiring` — чтобы напоминание приводило к действию.
8. **Самрегистрация по белому списку** (телефон + ДР при первом входе), если по-прежнему нужны эти данные: сейчас их вводит админ.
9. **#Rented в группу** — только если Станислав передумает (сейчас сознательно выключено 2026-11-08); альтернатива — read-only лента сделок в CRM, уже есть (`rented_text`).
